## 2. 后端选 Python/FastAPI 的论据

业务复杂度在「人设编译 + 记忆管线 + LLM 异步分析」，不在 Web 并发（母文档 §8 的 API 全是低频 CRUD + 分页）：

1. **核心逻辑主场**：PersonaCompiler（element→sign 差分继承、kb_version 钉扎、灰度）、脱敏规则、夜间 LLM 摘要，均为 Python 生态最成熟领域。
2. **MCP 一等公民**：memory-mcp 用官方 Python SDK 最成熟，与 xiaozhi-server（同为 Python）联调成本最低，全链路单一语言栈。
3. **vibe coding 适配**：Python 是 LLM 训练语料最丰富的语言；FastAPI decorator + 类型注解风格 AI 生成错误率最低；Pydantic 模型自动生成 OpenAPI，admin/app 可对 schema 生成客户端，形成闭环。
4. **资源画像匹配**：母文档给 web-api 的限额仅 0.5 核 / 0.75G，FastAPI（asyncio）绰绰有余；CPU 密集风险由「agent-worker 独立容器 + 并发=1」隔离，GIL 不构成问题。

### 候选对比

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| Python + FastAPI | MCP/LLM 生态最成熟；与小智同语言；AI 生成质量最高；开发速度快 | 并发性能弱于 Go/Node（本项目用不上）；GIL（worker 独立容器规避） | ✅ 选用 |
| TypeScript + NestJS | 类型安全；前后端同语言；有 MCP TS SDK | LLM 生态弱一截；框架重，AI 易过度设计；与小智异栈 | 备选（团队主力为 TS 时） |
| Go + Gin/Echo | 性能/部署最优 | 无高并发场景可用；MCP/LLM 生态最薄弱；业务迭代成本高 | ❌ |

## 3. 其余已定选型的优缺点

### PostgreSQL + pgvector（唯一业务库）

- 优点：单库覆盖关系 + JSONB（KB 分层差分）+ 向量（仅 memories 表）；事务保证 KB 发布 version++ 原子性；单机 4C16G 可承载。
- 缺点：向量量达百万级后弱于专用向量库；需关注 HNSW 索引内存。首版「向量只挂 memories」风险可控。

### PG SKIP LOCKED 队列（替代 Redis 队列起步）

- 优点：零新增组件、事务性出队、挂了不丢任务；样机期并发 1～2 足够。
- 缺点：高吞吐下不如专业队列；第二阶段拆 worker 机时迁移到 Redis Queue。

### 外部 ASR/LLM/TTS API（路线 A，不自研托管）

- 优点：无 GPU 成本、上线快、品质保底、故障域清晰。
- 缺点：成本随量线性增长；首字延迟受第三方制约；隐私链路多一环（需对齐供应商协议与「不存原始音频」承诺）。批量任务（摘要/记忆候选）应设计可切换的模型抽象层。

### xiaozhi-esp32-server 二次开发（钉 v0.9.6）

- 优点：OTA/激活/MQTT/WS 会话/智控台现成，固件零改动兼容。
- 缺点：Python+Java 混合、架构一般，魔改后难跟上游。纪律：定制收敛在三个注入点（persona_pack 拉取、旁路推送、远程 Memory MCP 挂载），封装为独立适配层，不改核心会话逻辑，不碰 Java 部分。

### Vue 3 + Element Plus（管理台）

- 优点：与小智智控台（Vue）同栈，外链观感一致；中文表单/表格场景 AI 生成最稳。
- 缺点：复杂交互生态弱于 React——管理台无此需求。

### 用户端框架（2026-08-01 修订）

~~Flutter~~（原建议，优缺点保留备查：四端单代码库、桌面端支持均衡、声明式 UI AI 生成一致性好；Dart 语料较少、桌面长尾插件需人工把关）。

**最终决策（以 ai-pet-app/docs/07 为准）**：Vue3 + Vite + TS strict + Pinia + axios + vite-plugin-pwa，演进路线 SPA→PWA→Capacitor。理由：与 admin 同栈复用、AI 语料最丰富、PWA 免分发即达，Capacitor 保留原生打包退路。

## 4. 日志方案（分阶段）

| 阶段 | 方案 | 说明 |
|------|------|------|
| V0.2（现在） | structlog JSON → stdout → Docker json-file 轮转（50m×5）→ Dozzle 查看 + cron 归档 OSS（180 天） | 零新增重量级组件 |
| 扩量后 | 阿里云 SLS（首选，同云合规、零运维、低量成本可忽略）或 Grafana Loki | 不自建 ELK（母文档已否决 ES）；不用海外 SaaS（日志含 device_id，出境违规） |

日志纪律（写进 AGENTS.md）：

1. 日志不落对话原文，只记元数据与 `content_redacted` 的 hash/长度；
2. 固定字段 `ts/level/service/trace_id/device_id/session_id/kb_version`，三服务以 trace_id 串联；
3. 日志与监控分离：可用性监控用 Uptime Kuma 或云监控免费额度。

## 6. vibe coding 配套纪律

1. **AGENTS.md 写死红线**：只存 content_redacted；agent 记忆默认 candidate 待审；KB 发布必须 version++；worker 禁进实时路径；分页强制 limit；日志不落原文。
2. **测试集中纯函数**：PersonaCompiler、脱敏规则、KB 差分继承必须 pytest 覆盖——vibe coding 唯一不能省的投资。
3. **CI 闸门**：ruff + mypy(strict) + pytest，AI 产出过闸再进主干。
4. **依赖钉版本**：lock 文件进仓；AI 新增依赖必须 review。
5. **迁移人工过目**：Alembic migration 可由 AI 生成，但必须人工 review 后执行。
