## 0. 先做：契约补齐（Epic C0，代码前）

需求分析发现 docs/06 契约与两端需求有 8 处缺口，**先改契约文档再写代码**（协作规则）：

| # | 缺口 | 决策 | 来源 |
|---|------|------|------|
| 1 | 记忆候选无「驳回」 | 加 `POST /devices/{id}/memories/{mid}/reject` | admin 02、app 02 |
| 2 | KB 反馈无「忽略」 | 加 `POST /admin/kb/feedback/{cid}/ignore` | admin 02 |
| 3 | 设备无「解绑/重命名」 | 加 `DELETE /devices/{id}`（解绑）、`PATCH /devices/{id}`（改名） | app 02 |
| 4 | 记忆无搜索 | `GET /memories` 加 `q`（标题/正文模糊）+ `status` 筛选 | admin 03、app P4 |
| 5 | 分页参数普遍缺失 | 所有列表端点统一 `limit`（默认 20 ≤100）+ `cursor`/`offset` | 红线 5 |
| 6 | persona_pack schema 未定 | 钉死 7 字段：`kb_version/system_prompt_fragments/style_constraints/taboo/default_emotion/blink_profile/retrieval_hints` | xiaozhi 03 |

## 2. 排期理由

1. **E1 先行**：所有接口都挂在 device 上，且 admin M1（Codex 在等）只差设备接口
2. **E2 是本项目灵魂**：人设注入是差异化价值，且是 xiaozhi-server 唯一的硬依赖；KB 种子不做，编译器无米下锅
3. **E3 紧随**：旁路通了才有真实对话数据，E4/E5/E6 才有原料；早通早暴露联调问题
4. **E4/E5 并行面小**可连做；**E6 依赖 E3 的数据**；**E7 最独立放后**
